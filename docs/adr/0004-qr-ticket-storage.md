# ADR-0004: QR Ticket Generation and Storage

**Status:** Accepted

## Context

A ticket needs to be both human-checkable (a confirmation code someone can read off
their phone at the door) and machine-scannable (a QR code for a faster check-in). The
QR image has to be generated somewhere, stored somewhere, and delivered to the attendee
both in their confirmation email and on a "view my ticket" web page -- without ever
being a publicly guessable URL.

## Decision

- **Generation:** `register_for_event` generates the QR PNG synchronously (pure
  computation via the `qrcode` + Pillow libraries, no external network call), immediately
  after the registration transaction commits. The QR encodes a URL --
  `{FRONTEND_BASE_URL}/tickets/{registrationId}?code={confirmationCode}` -- so scanning
  it at check-in opens the same ticket page a browser would.
- **Storage:** the PNG is uploaded to a private S3 bucket (`StorageStack`), block-public-
  access on, key `tickets/{eventId}/{registrationId}.png`. Nothing in this bucket is ever
  public.
- **Delivery, email:** `notify_on_registration` fetches the PNG from S3 and embeds it
  inline in the confirmation email via a MIME `Content-ID` reference, not a link. This
  sidesteps a real constraint: an S3 presigned URL signed with a Lambda's *temporary*
  execution-role credentials cannot outlive that role's session, so a long-lived link
  embedded in an email that might be opened days later would eventually 403. An inline
  image has no such expiry.
- **Delivery, web:** `register_for_event`'s initial API response and `get_registration`
  (the ticket-lookup endpoint, gated by `registrationId` + matching `confirmationCode`)
  both generate a **fresh, short-lived (15-minute) presigned GET URL** on every call,
  rather than persisting one. The ticket page always requests a new one when it loads.

## Consequences

- The `qrcode`/Pillow dependency (packaged as the `ticketing` Lambda Layer) is attached
  only to `register_for_event`, the one function that generates images --
  `notify_on_registration` only ever reads already-generated bytes from S3, so it stays
  on the lighter `common` layer alone.
- Confirmation-code-as-capability-token means a wrong or guessed code returns the exact
  same 404 as a nonexistent registration (see `get_registration`/`cancel_registration`),
  so the API never confirms whether a given `registrationId` is real.
- Ticket images are not deleted when a registration is cancelled (they're small, and
  keeping them doesn't leak anything not already visible via the ticket page); the S3
  lifecycle rule expires all ticket objects after 365 days regardless.
